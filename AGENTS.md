# Agent instructions

For AI agents (Claude Code, Codex, Copilot and others) working on this repository. `CLAUDE.md` imports this file, so every agent reads the same rules.

## What this project is

Gizmo Birdhouse turns an AI Thinker ESP32-CAM inside a 3D-printed birdhouse into a camera that photographs the birds that come to visit.

- `microcontroller/` is the PlatformIO firmware for the ESP32-CAM (OV2640 sensor, flash LED, microSD slot, 4 MB PSRAM). It watches the camera for motion, saves a photo of each visit on the microSD card, runs the Wi-Fi setup (from gizmo-common), and serves the web app and its API.
- `webapp/` is the Nuxt 4 web app, embedded in the firmware: the Visits, Live and Detection pages, the device card and the Wi-Fi setup. It extends the [gizmo-common](https://github.com/open-gizmo/gizmo-common) web layer, and the mock device in `webapp/server/` answers like the firmware during development.

## Structure

- `src/main.cpp`: the entry point; starts logging, the camera, the settings, the card, Wi-Fi, the clock, the web server and the detection.
- `src/camera`: starts the OV2640 and takes snapshots (`camera.*`), with the resolutions and the request options kept hardware-free in `capture_options.*`. The pins are in `camera_pins.h`. One snapshot is held at a time, shared by the web server and the detection task.
- `src/detection`: the task that watches the camera (`detection.*`): a QVGA frame every 700 ms, decoded at 1/8 into 40 x 30 grayscale pixels and compared with a background by the hardware-free `motion_detector.*`. On motion, it keeps the frame as the small picture of the visit and takes the photo.
- `src/visits`: the visits on the microSD card (`visit_store.*`, in 1-bit mode so GPIO4 stays the flash LED), with the file names (`visit_files.*`) and the list kept in memory (`visit_index.*`) hardware-free.
- `src/settings`: the settings of the detection (`birdhouse_settings.*`, hardware-free: defaults, thresholds, JSON) and their storage in `Preferences` (`settings_storage.*`), with the visit counter in a namespace of its own.
- `src/clock`: the time from NTP, so the visits have a date.
- `src/server`: the routes of the camera (`/api/camera`, `/api/capture`), the status (`/api/status`), the visits (`/api/visits...`), the settings (`/api/settings`, `/api/reset-settings`) and the embedded web app (the Wi-Fi setup and device routes come from gizmo-common).
- `src/wifi`, `src/config`, `src/serial`: the Wi-Fi setup names, the project name and web server, and the serial log.
- `src/webui`: generated by `npm run build:embedded`, never edited by hand.

## Working rules

1. Keep the split between firmware and web app clear: no device logic in the web app, no front-end behavior in the firmware.
2. Keep the module boundaries of `microcontroller/src/`: extend the right module instead of adding logic to `main.cpp`.
3. Keep hardware-free logic (`camera/capture_options.*`, `detection/motion_detector.*`, `visits/visit_files.*`, `visits/visit_index.*`, `settings/birdhouse_settings.*`) free of hardware headers, and test it with `pio test -e native`.
4. ArduinoJson 7 keeps a pointer to a `const char *` instead of copying it: copy any text that isn't a literal (`JsonString(text, JsonString::Copied)`).
5. When a route, payload or validation rule changes, update the firmware handlers, the mock device in `webapp/server/` and the web app together, and translate every new error ID.
6. Never read GPIO0 as a button: on the ESP32-CAM it is the clock of the camera. The microSD card stays in 1-bit mode: the 4-bit mode takes GPIO4, the flash LED.
7. Slow card work (removing many files) belongs in the detection task, never in a web server handler: the async server must answer quickly.
8. Prefer small, hardware-aware changes: no blocking calls, no needless allocations, no broad refactors unless they are needed.

## With every change

1. **Write the changelog.** When a maker would notice the change (a feature, the web app, the hardware or wiring, the setup steps, a fix), add a line under `## Unreleased` in [CHANGELOG.md](CHANGELOG.md), in the same commit. Write it for the people who flash and use the gadget, not as a commit message: what changed for them, and what they need to do (flash again, rewire, set something up again). Internal changes (refactoring, tests, CI) need no line unless they change what the gadget does.
2. **Keep the docs in sync.** Update the README (and its screenshots in `docs/` when the web app looks different), and tell the user when the gadget's page on [opengizmo.dev](https://opengizmo.dev) needs the same change.
3. **Check it before calling it done.** Run the tests (`pio test -e native` in `microcontroller/`, `npm test` in `webapp/`) and the release build (`npm run build:embedded` in `webapp/`, then `pio run -e release`).

## Releasing

Follow "Releasing a new version" in the README. The version's notes must be moved from `## Unreleased` to a `## vX.Y.Z - YYYY-MM-DD` heading in CHANGELOG.md: they become the GitHub release notes, and the release workflow stops before building anything when they are missing or when notes are left under Unreleased.

Every OpenGizmo gadget has its own release workflow file, and they are kept the same apart from the gadget's name and module (chip), which sit in the `env` block at the top. When you change one, make the same change in the others.

Work on the `feature` branch; changes reach `develop` and then `main` one step at a time, only for a release.
